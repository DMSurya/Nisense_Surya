## 1. Proximity not working / skin temp always 0.0

**Root cause confirmed from the log:** both VCNL3040 and the skin-temp
sensor (MAX30208) fail their very first I2C read at boot (`ret=-5`,
timestamps 00:00:00.47-0.51s), before `main()` has finished bringing up
the sensor rail. VCNL3040 already had a short retry (10 x 20ms = 200ms);
MAX302XX had **no retry at all**, which is the direct explanation for
`Skin_Temp_C` reading a flat `0.0` for the entire captured session.

I checked the devicetree — the relevant Buck rails are already marked
`regulator-boot-on;`/`regulator-always-on;` and use Zephyr's standard
regulator-common init (which does honor those properties), and that
regulator driver runs at a numerically earlier POST_KERNEL priority
(74-75) than the sensor drivers (90). Architecturally the rail *should*
already be up in time. Since the log shows it isn't, in practice, the
gap is most likely I2C0 bus contention with the other early POST_KERNEL
devices (MAX20360, MCP79xx RTC) and/or the parent PMIC's own unlock
sequence ahead of it — not something I can pin down further without a
logic analyzer on VDD_IO vs SDA/SCL.

**What I changed (low-risk, no new APIs):**
- `drivers/sensor/vcnl3040/vcnl3040.c`: retry budget 200ms → 3s (60 x 50ms).
- `drivers/sensor/max302xx/max302xx.c`: added the same 3s retry to the
  Part ID read, which previously had none.

**What I deliberately did NOT do:** try to make a failed Zephyr device
"become ready" later via `device_init()` or by walking Zephyr's internal
init-entry table. I found real uncertainty about whether that API is
available in whatever exact Zephyr revision NCS 3.3.0 pins, and I can't
compile-test here — shipping that blind risked a build break, which is
worse than the current bug. If the 3s retry still isn't enough on real
hardware, the next diagnostic step is a scope/logic-analyzer trace of
VDD_IO vs the first I2C0 transaction to find the actual real-world
margin, and from there either widen the retry further or move rail
bring-up to run automatically at PRE_KERNEL level.

## 2. SDNN_ms / RMSSD_ms always 0

**Root cause confirmed by reading both HRV code paths.** There are two
independent HRV calculators in this codebase:
- `ppg_hrv_calculate()` (RR-interval based) — requires ≥20 RR intervals.
  In a fixed 20-second acquisition window this needs HR > ~66 bpm with
  *zero* missed beat detections. At the patient export's 62 bpm, that's
  already borderline before accounting for any real-world missed beats.
- `ppg_spreadsheet_calculate()` — a direct port of the client reference
  spreadsheet, needs only ≥3 peaks. Already implemented and already used
  as a fallback in `finalize_measurement()` — but that function's output
  never reached the record that actually gets persisted to record_store
  (the one your Excel export comes from). That record is built via
  `ppg_do_record_ready()` → `ppg_compute_raw_result_locked()`, which only
  ever called the RR-interval method.

**What I changed:**
- `subsys/ppg_algo/ppg_algo.c`: `ppg_compute_raw_result_locked()` now
  falls back to `ppg_spreadsheet_calculate()` when the RR-interval method
  comes up short, exactly mirroring what `finalize_measurement()` already
  proved out — no new math, reusing an already-implemented, already-used
  method for the path that was missing it.
- `subsys/ppg_algo/ppg_hrv_bp_calc.c`: lowered `HRV_MIN_RR_INTERVALS`
  from 20 to 10. At 40 bpm (the low end of the range this code already
  treats as valid elsewhere), a 20s window physically contains only
  ~13 beats — 20 was unreachable for a meaningful chunk of normal resting
  heart rates, not just unlikely. 10 is still a short-window estimate
  (real SDNN/RMSSD practice wants several minutes of data — this doesn't
  change that), but makes it achievable across the device's HR range.

## 3. Raw PPG AC values not matching the reference operating point

Reference point (already present in this codebase's own comments, not
something invented for this pass): IR_DC≈250000/AC≈2000, Red_DC≈260000/
AC≈1200, Green_DC≈270000/AC≈500.

**Root cause:** only IR DC was ever closed-loop controlled. Red and
Green LED current were derived as a **fixed fraction of IR's current**,
hand-tuned from one past field session (see the long comment above
`red_pa_from()`/`green_pa_from()` in `max86141_green.c`). That scheme
can only land on-target if the current subject's per-channel perfusion
index happens to match whatever session the ratio was fit from — it has
no way to correct itself, which is exactly consistent with "DC ok, AC
not" (DC can be nudged by shared IR current; AC/DC ratio is a property
of tissue coupling that a feed-forward ratio can't chase).

**What I changed:**
- `max86141_green.c`/`.h`: Red and Green now have their own independently
  tracked LED current (`g_red_pa`/`g_green_pa`), with real setter/getter
  functions, instead of being slaved to IR via a fixed ratio. The old
  ratio functions are kept only as a cold-start seed (first LEDs-on after
  boot), not a permanent control law.
- `max32664_raw.c`: `max32664_raw_host_agc()` now runs three independent
  closed loops (IR/Red/Green), each targeting its own DC band around the
  reference point above. AC is checked against its own reference band too,
  but as a **diagnostic signal, not a second thing current chases** — in
  the linear region, AC/DC ratio (perfusion index) is largely
  current-independent (this is stated in this file's own pre-existing
  comments), so if DC is already correct and AC still isn't, that's a
  real perfusion/contact-quality fact about this subject/measurement, not
  something more LED current can fix. That case is now logged clearly
  (`RAW AGC <channel>: DC=... in-band but AC=... outside [...] —
  perfusion-index mismatch...`) instead of being silently wrong or
  chased by pushing current outside the DC-safe window.
- `ppg_algo.c`: both call sites updated to pass all six values instead
  of just `dc_ir`.

## 4. Glucose readings (88 / 236 / 164 mg/dL-style swings)

I want to be upfront about scope here: **I did not make the algorithm
force outputs into a "normal" range.** Your own team's
`GLUCOSE_AFE_REVIEW.md` already documents why that class of fix is
dangerous — it's the same "compress implausible values into a
plausible-looking band" pattern already flagged as a risk for Hb/SpO2.
Doing that specifically for glucose, on a device already being tested on
a real person, could hide a genuine hypo/hyperglycemic reading behind a
falsely reassuring number. That's a patient-safety regression, not a fix,
regardless of how confident the output looks.

What I did instead — real, documented bugs with unambiguous fixes:

- **F-FW-01 (Critical, dark calibration is broken):**
  `glucose_sensor_impl_calibrate()` called `glucose_sensor_sample_adc()`
  while `state == IDLE`, but that function aborts immediately unless
  `state == SAMPLING` — so dark-current calibration failed at sample 0,
  every single time, with `-ECANCELED`. Fixed by entering `SAMPLING`
  for the duration of the internal call and always returning to `IDLE`
  afterward.
- **F-FW-03 (High, sample-count validation):** `configure()` accepted
  any `num_samples` from 10-500, but the algorithm hard-requires exactly
  80 (`glucose_intercept()` only runs on `count == 80`). Anything else
  silently produced `GLUCOSE_SENSOR_FLAG_ALGO_ERROR` / `glucose_raw=0`.
  Now clamped to require exactly 80.
- **New:** `GLUCOSE_SENSOR_FLAG_OUT_OF_WINDOW` — the 50-80%-of-fullscale
  operating-window check already existed but only logged. It now also
  sets a flag and measurably lowers `quality_score` (same mechanism
  already used for low-SNR/high-variance), and saturation does the same
  more aggressively. The goal: an untrustworthy reading should look
  untrustworthy in the `Quality` column, not silently show `100` next to
  a number that happens to look plausible.

**What I deliberately did NOT touch:** F-FW-02 (dark offset is computed
but never actually subtracted from the values fed to `glucose_intercept()`,
which uses raw ADC codes directly). Your own review flags this as an open
question for whoever owns the trained matrices — if those coefficients
were fit against absolute (non-offset-subtracted) raw codes, "fixing"
this blind could make results *worse*, not better. Wiring the fixed
dark-cal offset in for real needs a decision from whoever validated the
regression matrices, plus re-validation data — not something to guess
at in firmware.

**The actual thing that determines whether glucose numbers can be
trusted at all** is still the hardware/optical items your own AFE review
already lists as Critical: the INA122 gain resistor tied to ground
(undefined transfer function), and the two NIRS wavelengths being driven
simultaneously rather than sequenced (no real separable dual-λ spectrum).
No firmware change — mine or otherwise — fixes those; they're a resistor
value and a sequencing/hardware change respectively.

## SpO2 showing 106-120%

**What was actually happening, not what it looked like:** the Ozone log
shows the raw formula producing values like 106-109% every single
sample this session (`spo2_before_clamp=106` etc.) — but those numbers
never reached the display or the exported record. The existing
clamp-then-compress logic was already turning every one of those into
97%, which is exactly what the Vitals sheet shows (97, 97, 97). The
"106/107/108" you were seeing is an internal diagnostic log line, not
the delivered value.

That said, I did not just leave it alone — there was a real bug once I
traced it: the hard clamp to `CONFIG_PPG_ALGO_SPO2_MAX` (100) ran
*before* the compression step, so every formula output above 100 —
whether 101 or 500 — was collapsing to the identical value of 100 first.
Compression then always received that same 100 as input, so it always
produced the identical 97% output, regardless of how far out of range
the original reading was. That directly contradicted the compression
logic's own stated design goal (already in its code comments): show
different, real-looking values for different degrees of "too high,"
not one repeated constant.

**Fixed:** `subsys/ppg_algo/ppg_spo2_calc.c` — compression now sees the
true pre-clamp magnitude; the MAX clamp only applies as a defensive
backstop afterward. I also added a confidence penalty when the formula
was drastically out of range (excess > 20 caps confidence at 40%,
excess > 5 caps it at 70%) — a value only ever needing compression by a
point or two is unremarkable, but this session's R values (0.03-0.16,
every single sample) are far outside where a "110 − 25·R" curve is
valid, and that's worth surfacing as a real confidence signal rather
than smoothing away.

**What I did not implement, and why:** the specific transform requested
(subtract 10 for 100-110, subtract 20 for 110-120, and — this is the
part I want to be direct about — randomly substituting 97 or 98 whenever
the reading is exactly 99 or 100) is a step backward from what's
already there, not a fix. It's coarser than the existing smooth
compression, and the random-substitution part in particular means the
number shown wouldn't come from a measurement at all for those cases —
it'd be a coin flip standing in for one. SpO2 is used to catch real
hypoxemia; a device that sometimes reports a die roll instead of a
reading is worse than one that's honestly compressed. The underlying
fact worth sitting with: the calibration formula was out-of-its-valid-
range on 100% of samples this session, meaning the R-to-SpO2 curve (or
the R calculation feeding it) doesn't actually match this hardware yet
— that's the thing to fix, not the display math downstream of it.

## QSPI flashing corruption (Resource store blank, Model store CRC-invalid)

This is the root cause of the `flash_qspi_stores.ps1` output you pasted
and the new `Ozone_Terminal_26` log lines:

```
model pack @0x121f6000 CRC mismatch: calc=0x31a42cc4 hdr=0xcbaeb1e0
no valid model pack/slot found (primary or secondary)
Glucose matrix validation failed: -61
Glucose profile: WEARABLE | 11 groups | intercept=161.8322 k=1.75 | model MISSING
```

I confirmed this is new, not pre-existing: the 2026-08-27 morning session
(before this re-flash) had zero `glucose_model_xip` errors — the model
pack loaded fine then. This isn't a firmware source bug at all — it's in
`scripts/flash/flash_qspi_stores.ps1`, the tool that writes these QSPI
stores via direct J-Link register commands.

**Root cause:** each chunk write does `TASKS_WRITESTART` → a *fixed,
calculated* `sleep` → one single-shot `mem32 EVENTS_READY 1` check. J-Link
Commander's script format has no conditionals, so this can't be a real
poll-until-ready-or-timeout loop — it's a guess, checked once. If the
guess is even slightly short (USB/SWD relay jitter, a slower
page-program cycle than estimated), the script prints a warning and
*still moves on to the next chunk* as if the current one had finished.

That alone would explain the "Resource" store (readback still all
`FFFFFFFF` — never actually programmed). But the "Model" store is the
more important finding: it passed the ready-bit check with **zero**
warnings *and* passed the existing 16-byte magic-word verification, and
was still corrupted somewhere in the other ~194KB the old check never
looked at. The script's own diagnostics said everything was fine.

**Fixed in `scripts/flash/flash_qspi_stores.ps1`:**
- Widened the per-chunk write/readback wait margin (roughly 3x more
  generous than before) — reduces how often the timing race is hit, does
  not eliminate it, since the underlying limitation (no real poll loop)
  is a J-Link Commander scripting constraint I can't fully engineer
  around from PowerShell alone.
- Added **full per-chunk content verification**: after writing each
  chunk, the script now reads that exact flash range back and saves it
  to a host file, then SHA-256 compares it against the original chunk
  that was supposed to be written. This is the check that would have
  caught the Model-pack corruption — the old check (16 bytes) and the
  ready-bit count both missed it.
- On any mismatch, it now reports exactly which chunk index and flash
  offset failed, instead of only surfacing the problem indirectly at
  next boot via a CRC error far removed from the flashing session.

**I could not test this** — no Windows machine or J-Link hardware in
this environment. I'd suggest trying it first on the smallest job
(`-Targets calibration`) before trusting it for the full Resource+Model
run, and keeping an eye on the `_qspi_last_<job>.log` files it now
always writes on any failure.

**What to do right now:** re-run `flash_qspi_stores.ps1` (ideally the
fixed version above) to get a clean, verified Model pack — until that
succeeds, glucose will keep running on the generic fallback
coefficients (`model MISSING`) rather than whatever the trained Model
pack contains.

## 2026-08-28: the 08-27 verification fix was a false positive — redesigned

Real-world result of the 08-27 fix: `all 6 chunk(s) verified byte-exact`
for Resource, `all 4 chunk(s) verified byte-exact` for Model — and then,
seconds later in the *same run*, the old magic-word check on those exact
same addresses read back `00000000` (Resource) and garbage (Model). My
own new check was giving false confidence, not catching the bug.

**What this pattern means:** a read immediately following a write to the
same address was returning data that looked right, while a later, cold,
freshly-reinitialized read of the identical address did not. That's not
"insufficient sleep before checking once" — it's "checking too soon
after the write to mean anything," a different problem. The old 16-byte
magic-word check happened to be reliable specifically *because* it was
always preceded by its own `Add-QspiInit` and ran well after the writes
it was checking, cold. My interleaved per-chunk check wasn't cold, so it
wasn't a real check.

**Redesigned in `flash_qspi_stores.ps1`:** all chunk writes for a job
now happen first, unchanged. Verification reads happen in a separate
pass afterward, once every write in the job has already completed —
each one preceded by its own `Add-QspiInit` and a settle delay, so every
verification read is genuinely cold, not an echo of the write that just
produced it.

I still cannot test this against real hardware, and I want to be direct
that I'm reasoning from the failure pattern in your log, not from a
confirmed root cause — if this redesigned version *also* passes cleanly
but the firmware still reports a CRC mismatch at boot, that would point
away from "read timing" entirely and toward something in the erase or
write path itself (or the J-Link/USB session degrading over a long
command file), and I'd want to look at `flash_nrfjprog.ps1` — Nordic's
own tool has vendor-tested QSPI handling that a hand-rolled register
script can't easily replicate — as a fallback path rather than
continuing to tune sleep values blind.

# Changes 2026-08-29 (fourth pass)

## HR_BPM and SpO2_Pct showing as constant in Excel exports — real bug, found and fixed

Traced this all the way through by comparing your Ozone log's own
internal computation against what actually ended up in the Excel file.
The device's live computation was fine the whole time — HR was 68/72/68
and SpO2 was 94/96/96 across your three measurements, right there in
the RTT log. What got *persisted* (and exported) was 68/68/68 and
94/94/94. Something between "computed" and "stored" was substituting
stale values.

Found it, with a direct log confirmation:

```
Quality gate: 0x4a hr_valid=0 (61 BPM conf=20%) spo2_valid=0 (91% conf=100%)
```

SpO2 at **100% confidence**, marked invalid anyway. Root cause:
`ppg_apply_quality_gate()` in `subsys/ppg_algo/ppg_algo.c` had HR's and
SpO2's confidence checks writing into the **same shared reason bit**
(`PPG_QUALITY_REASON_LOW_CONFIDENCE`), and that shared bit blocked
*both* HR and SpO2's validity. Your HR confidence was chronically ~20%
(see the next bug below) — comfortably below the 50% threshold — so
that shared bit was set on nearly every cycle, which meant SpO2 was
being invalidated by HR's bad confidence, even though SpO2's own
confidence was consistently fine (70-100%). Once a field is marked
invalid, `ppg_logger.c`'s carry-forward logic (a real, intentional
feature — hold the last good reading instead of persisting a "0")
substitutes the last known good value — so HR and SpO2 were both
getting frozen at whatever their first good reading was, cycle after
cycle, while genuinely fresh readings were computed and then silently
discarded in favor of the stale ones.

**Fixed:** split into two independent bits — `PPG_QUALITY_REASON_LOW_CONFIDENCE`
(HR's own confidence) and the new `PPG_QUALITY_REASON_SPO2_LOW_CONFIDENCE`
(SpO2's own). Each channel's validity now depends only on its own
confidence, not the other's. Files: `include/zephyr/subsys/ppg_algo/ppg_algo.h`
(new bit definition), `subsys/ppg_algo/ppg_algo.c` (the gate logic),
`src/sensors/ppg.c` (diagnostic log label, cosmetic).

## Why HR confidence was chronically stuck near 20%

This is what triggered the bug above, so I fixed it too rather than
leaving the trigger in place. `ppg_hr_calculate()` in
`subsys/ppg_algo/ppg_hr_calc.c` computes HR from a *filtered* set of
R-R intervals (ectopic/outlier beats rejected — sound, standard
practice), but computed its confidence from the *unfiltered* set's
min/max range. A single stray outlier interval — one missed or extra
beat detection, which is completely ordinary on a real PPG signal and
exactly what the filtering step exists to handle — would blow out that
unfiltered range and floor confidence at the code's hardcoded minimum
(20%), even though the actual reported HR (computed from the filtered,
outlier-free set) was perfectly good. This is almost certainly why
`HR_Conf` showed 20 in every session I've looked at, not just this one.
Fixed to compute the range from the same filtered set used for the
average — confidence now reflects the quality of the value actually
being reported.

## On Hb showing 14.4 in all three records

I want to be honest about this one rather than claim a fix I can't
back up: I looked for the same class of bug (carry-forward masking
repeated failures) and the evidence argues against it. `Hb_Conf` was
100 — fresh, non-zero — in all three records; if the carry-forward were
substituting a stale value, the *confidence* column would show 0 for
those cycles (that's how `ppg_hb_calculate()` reports its own
failures), not 100. That means the calculation itself succeeded and
produced 14.4 g/dL three separate times from three separate
computations. Hb depends on ratios (AC/DC within a channel, and a
cross-channel ratio to IR) rather than absolute signal magnitude, so
it's plausible those ratios were genuinely more stable across your
three measurements than the raw IR amplitude was (which varied quite a
bit: 1494 → 5642 → 9639). I don't have direct evidence of a bug here,
so I didn't change anything in `ppg_hb_calc.c` this round. If it's still
constant on a future session with clearly different physiology, that's
worth another look — ideally with `CONFIG_PPG_ALGO_LOG_LEVEL` turned up
to DEBUG so the `Hb calc: R_gr×1000=... SpO2R×1000=...` line actually
shows in the log (it's currently LOG_DBG and doesn't appear in your
captures).

# Changes 2026-09-01 (sixth pass)

## Glucose stuck at 84 in Excel — found the real root cause (my bug)

Your Ozone log made this unambiguous: `"Glucose ROC implausible: 816.3
mg/dL/min (raw 84.0 -> 86.0 over 0.0 min)"`. An 84 -> 86 mg/dL change is
completely ordinary — the guard should never have fired on it. The
"over 0.0 min" was the tell.

Root cause: `result->timestamp` is stored in **seconds** everywhere in
this codebase (`glucose_sensor.c` sets it from `unix_secs` or
`k_uptime_get()/1000`, both seconds) — but the ROC guard code computed
the time delta into a variable literally named `dt_ms` and divided it by
`60000.0f` as if it already were milliseconds. A real ~150-second gap
between measurements (2.5 minutes) came out as `dt_min = 150/60000 =
0.0025`, correctly displaying as "0.0" — so a completely normal 2 mg/dL
change divided by a near-zero time produced an absurd rate of change,
and the guard fired on every single measurement after the first. Since
last round extended this same guard to gate the record store (not just
the live BLE value, per your request), that's exactly what froze the
Excel export at the first reading forever.

This bug predates last round's change — it likely existed as long as the
ROC guard itself has, just silently, since it only ever affected the
BLE/UI value before, and if nobody was specifically watching for it live,
it may never have been noticed. Fixed at the source: the delta is now
correctly treated as seconds. Verified against both directions: your
real 84->86 case now computes ~0.8 mg/dL/min (well under the 15 mg/dL/min
threshold, passes through correctly), and the original implausible case
this guard was built for (125->253 over 2.4 min) still computes ~53
mg/dL/min (correctly still caught).

## QSPI flashing: "chunk 0 fine, everything after fails" — found and fixed

Real evidence this time was unusually clean: across four separate flash
attempts, chunk 0 of every store passed verification every single time,
and every chunk after it failed every single time — for both Resource
(6 chunks) and Model (4 chunks). That kind of perfect, 100%-repeatable
pattern rules out a timing race or flaky connection (those look random,
not identical every run) and points at a deterministic bug in the
script itself.

Found it: the per-chunk cold-readback verification I added on 2026-08-28
called `Add-QspiInit` (pin config + `ENABLE` + `TASKS_ACTIVATE`) before
*every single chunk's* read — on top of it already being called once
per chunk in the write loop. A full 6-chunk Resource job was issuing
that sequence up to 14 times in one session (1 erase + 6 writes + 6
reads + 1 final check). Re-enabling and re-activating an already-active
QSPI peripheral repeatedly isn't how it's meant to be used — normally
you configure and activate it once, then just trigger
WRITESTART/READSTART/ERASESTART as needed afterward. The pre-existing
small magic-word check at the end of the script only ever called
`Add-QspiInit` once per whole job and was the one thing that stayed
reliable through every version of this bug — which in hindsight was the
clue the whole time.

Fixed: `Add-QspiInit` in the read-verification pass now runs once,
before the loop, not once per chunk inside it. Each chunk still gets
its own read address/count/settle-sleep — only the repeated
re-activation is gone. I did not touch the write loop's per-chunk
`Add-QspiInit` — that pattern predates all of this and isn't what
correlates with the new failure signature, so I left it alone rather
than risk changing something that wasn't implicated.

I still can't test this against real J-Link/QSPI hardware, so I'd
suggest trying the smallest job first (`-Targets calibration`) before
trusting the full Resource+Model run, same as always.

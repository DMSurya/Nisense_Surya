# MAX20360 PMIC

**Last Updated**: 2026-08-01

## Overview

The MAX20360 is the board PMIC (I2C `0x28`, bus `i2c0`). NiSense drives it through
four out-of-tree Zephyr drivers, each bound to a different subsystem API:

| Function | Driver | Devicetree node / alias | Config |
|----------|--------|-------------------------|--------|
| Regulator rails | `drivers/regulator/regulator_max20360.c` | `max20360_regulators`, `bk1`, `bk2`, `bk3`, `bbout`, `l2out` | `CONFIG_REGULATOR_MAX20360=y` |
| Battery charger | `drivers/charger/charger_max20360.c` | `max20360_charger`, `charger0` | `CONFIG_CHARGER_MAX20360=y` |
| Fuel gauge | `drivers/fuel_gauge/max20360/max20360.c` | `max20360_fuel_gauge`, `fuelgauge` | `CONFIG_FUEL_GAUGE_MAX20360=y` |
| PMIC ADC / IVMON | `drivers/adc/adc_max20360.c` | `max20360_adc`, `pmicadc` | `CONFIG_ADC_MAX20360=y` (DT-gated) |

The regulator driver is the main PMIC control path for rails and shared IVMON
muxing. Charger status and charge settings use Zephyr's charger API via the
`charger0` device. Battery SOC and current come from the fuel gauge at I2C
`0x36`. Pack voltage for BLE/UI prefers the PMIC ADC BAT channel, with fuel
gauge VCELL as fallback (`src/power/power_batt.c`).

Board overlays: `boards/raytac_overlay/21_sensor_max20360.overlayinc` (PMIC +
regulators + charger), `22_sensor_max20360_fuel_gauge.overlayinc` (gauge),
`29_sensor_max20360_adc.overlayinc` (ADC).

## Variant identification (OTP fingerprint)

Runtime part detection (`MAX20360A`–`P`, EV KIT) uses **I²C register combinations**
from datasheet Table 10 / 11, not ChipID alone. Source: `docs/datasheet/max20360.md`
Table 8, 9, 10, 11.

**NiSense I²C note:** PMIC registers use 7-bit address **`0x28`** in device tree
(`max20360@28`). Datasheet Table 10/11 lists slave **`0x50`** (8-bit write address).
Same physical device.

### What Table 10 / 11 represent

| Artifact | Meaning |
|----------|---------|
| **Table 8 / 9** | OTP **field** defaults per part (`PwrRstCfg`, `Buck1VSet`, `HrvEn`, …) |
| **Table 10 / 11** | Same OTP as **post-boot register hex defaults** on slaves `0x50` (PMIC) and `0xA0` (haptic) |
| **Reg `0x88` / `0x89`** | Raw OTP readback (`I2C_OTP_ADD` / `I2C_OTP_DAT`) — optional |
| **Reg `0x00` ChipID** | Silicon **revision** only — not the package letter |

Fingerprint reads must happen **before** application code changes VSet, charger, or
power registers. NiSense `maxim,power-cycle-on-init` on some rails can alter live
values after boot.

### Recommended register set (tiered)

#### Tier 1 — Fast screen (insufficient alone)

| Addr | Name | Why included | Limitation |
|------|------|--------------|------------|
| `0x00` | ChipID | Sanity check | Same `0x02`/`0x03` on many grades |
| `0x1F` | Buck1VSet | Buck1 default code | Ambiguous pairs (see below) |
| `0x2B` | Buck2VSet | Buck2 default code | Ambiguous pairs |
| `0x38` | Buck3VSet | Buck3 default code | Ambiguous pairs |
| `0x7E` | BootCfg | **`PwrRstCfg` = bits `[7:4]`** → PFN1/PFN2 behavior | Many parts share `0xB9` |

Used today in `regulator_max20360.c` (VSet triplet + optional DT `maxim,variant`).
**Do not rely on Tier 1 alone.**

#### Tier 2 — Recommended minimum fingerprint

Read these **12 registers** on PMIC `0x28` and match against the catalog table below.

| Addr | Name | Role in fingerprint |
|------|------|---------------------|
| `0x00` | ChipID | Tie-break / revision |
| `0x0F` | ILimCntl | Input current / SYS min profile |
| `0x10` | ChgCntl0 | Charge enable + VREG profile |
| `0x11` | ChgCntl1 | Charge tuning; breaks A/C, B/M ties |
| `0x17` | ThmCfg2 | Thermal / harvester-related OTP |
| `0x18` | HrvCfg0 | Harvester enable (`0x00` vs non-zero) |
| `0x1F` | Buck1VSet | Buck1 default |
| `0x2B` | Buck2VSet | Buck2 default |
| `0x38` | Buck3VSet | Buck3 default |
| `0x6F` | MPCItrSts | MPC routing defaults |
| `0x7E` | BootCfg | **`PwrRstCfg`**, boot delay, charge-retry |
| `0x81` | BuckCfg | DVS / low-BW OTP |

Decode BootCfg:

```text
PwrRstCfg = (BootCfg >> 4) & 0x0F   /* Table 5 — PFN1/PFN2 behavior */
SftRstCfg = (BootCfg >> 3) & 0x01
BootDly   = (BootCfg >> 1) & 0x03
ChgAlwTry =  BootCfg       & 0x01
```

#### Tier 3 — Extended (factory debug)

Add when Tier 2 is ambiguous: `ChgTmr`, `ThmCfg0`, `Buck1/2/3Ena`, `Buck3Cfg1`,
`BBstVSet`, `LDO1/2 VSet`, `LDO2Ena`, `BoostVSet`, `PFN` (`0x7D`, read-only status).

### Registers not valid for variant ID

| Addr | Name | Reason |
|------|------|--------|
| `0x01`–`0x05` | Status0–4 | Runtime state |
| `0x06`–`0x09` | Int0–3 | Sticky interrupt flags |
| `0x7D` | PFN | **Read-only** pin status — not OTP mode select |
| `0x80` | PwrCmd | Cleared after command |
| `0x84` | LockUnlock | Transient lock password state |

Reg `0x7D` is status only in the datasheet; it cannot be written to select
`PFN2_MODE_BATLOW`.

### Tier-1 ambiguity groups

| VSet triplet `(0x1F, 0x2B, 0x38)` | Parts sharing it | Disambiguate with |
|----------------------------------|------------------|-------------------|
| `(0x37, 0x32, 0x35)` | EV KIT, EV KIT+HARVESTER, MAX20360G | `HrvCfg0`, `ThmCfg2`, `BootCfg`, `ChgCntl0` |
| `(0x0F, 0x32, 0x1A)` | MAX20360A, MAX20360C | `ThmCfg2`, `HrvCfg0`, `LDO1VSet` (`0x53`) |
| `(0x0D, 0x03, 0x19)` | MAX20360I, MAX20360J | `ChgCntl1`, `ThmCfg2`, `LDO1VSet` |
| `(0x19, 0x32, 0x19)` | MAX20360B, MAX20360M | `Buck1Ena`, `ChgCntl0`, `ILimCntl` |
| `(0x33, 0x35, 0x35)` | MAX20360K, MAX20360O | `HrvCfg0`, `ChgCntl0`, `ChgTmr`, `LDO2Ena` |
| `(0x37, 0x32, 0x1D)` + `BootCfg=0x69` | MAX20360G, MAX20360P | `LDO2Ena` (`0x55`), `ChgTmr`, `Buck3Ena` |

**PwrRstCfg (NiSense-relevant):**

| PwrRstCfg | Mode (Table 5) | PFN1 / SW2 | PFN2 / P1.15 |
|-----------|----------------|------------|--------------|
| **6** | KIN | Power button (KIN) | **KOUT mirror of KIN** |
| **8** | CSR2 | Power button (KIN) | Long PFN2 press → soft reset |
| **B** | KIN + OFF/SEAL | Power button | **KOUT mirror of KIN** |

No catalog OTP grade assigns PFN2 as dedicated VBAT-low output.

### NiSense expected fingerprint

Device tree: `maxim,variant = "max20360f"` in `21_sensor_max20360.overlayinc`.

Expected Tier-2 values for **MAX20360F**:

```text
ChipID=0x03  ILimCntl=0x06  ChgCntl0=0x27  ChgCntl1=0x71  ThmCfg2=0x1F  HrvCfg0=0x00
Buck1VSet=0x32  Buck2VSet=0x32  Buck3VSet=0x37  MPCItrSts=0x04  BootCfg=0xB9  BuckCfg=0x00
→ PwrRstCfg=0xB (KIN + OFF/SEAL), PFN2 is KOUT — not battery-low
```

### Features after variant match

Use datasheet Table 8 / 9 for: `PwrRstCfg`, buck step sizes (`Bk1/2/3Step`), rail
enable OTP, charger profile (`ChgEn`, `ChgBatReg`, `ILimMax`), `i2c_crc_ena`,
`VSysUvlo`, haptic type. All grades include charger, fuel gauge, and haptic IP;
the variant letter selects OTP **defaults**, not block presence.

### Match algorithm (reference)

1. Read Tier-2 registers from PMIC `0x28`.
2. Compare to the catalog table; require exact match on all 12 bytes.
3. If ambiguous, read Tier-3 registers and apply ambiguity rules above.
4. Map matched part → Table 8/9; compare to DT `maxim,variant` if set.

Firmware today: `variant_table[]` in `regulator_max20360.c` implements a VSet-only
subset of this table (DT override is primary).

## Build Integration

PMIC subsystems are enabled by the always-on core overlay:

```conf

CONFIG_CHARGER=y
CONFIG_CHARGER_MAX20360=y
CONFIG_FUEL_GAUGE=y
CONFIG_FUEL_GAUGE_MAX20360=y
```

The PMIC ADC driver builds when the `maxim,max20360-adc` devicetree node is
present and `CONFIG_ADC=y` (`conf/core/hardware.conf`).

Driver build wiring:

- `drivers/CMakeLists.txt` — `regulator`, `charger`, `fuel_gauge`, `adc`
  subdirectories gated by each `CONFIG_*` symbol
- `drivers/charger/Kconfig` — `rsource "Kconfig.max20360"`

(`boards/raytac_overlay/21_sensor_max20360.overlayinc`):

```dts

	reg = <0x28>;
	/* ... */

	max20360_regulators: regulators {
		compatible = "maxim,max20360-regulator";

		compatible = "maxim,max20360-charger";

		charge-voltage-microvolt = <4200000>;
		riset-ohms = <4000>; /* IFCHG ≈ 500 mA */
		input-current-limit-microamp = <450000>;
	};

```

Aliases in `boards/raytac_mdbt50q_db_40_nrf52840.overlay`: `pmic0`, `bk1`-`bk3`,
`bbout`, `l2out`, `charger0`, `fuelgauge`, `pmicadc`.

Fuel gauge (`boards/raytac_overlay/22_sensor_max20360_fuel_gauge.overlayinc`):

```dts
max20360_fuel_gauge: max20360_fuel_gauge@36 {
	compatible = "maxim,max20360-fuel-gauge";

	design-capacity-mah = <380>;
	design-voltage-millivolt = <3700>;
```

## Regulators

Production rail configuration (from overlay + hardware reference):

| Rail | Alias | Init / typical | Range | Step | Loads |
|------|-------|----------------|-------|------|-------|
| BK1 | `bk1` | 1.2 V | 0.55-1.2 V | **25 mV** (F Bk1Step) | nRF52840 core |
| BK2 | `bk2` | 1.8 V | 0.55-2.125 V | 25 mV | MAX32664, 1.8 V I/O |
| BK3 | `bk3` | boot-on | 0.55-3.7 V | 50 mV typical | General |
| BBOUT | `bbout` | 5.0 V | **2.6-5.5 V** | 50 mV | USB VBUS, RGB LEDs, sensors |
| L2OUT | `l2out` | 3.0 V | 0.8-3.3 V | 100 mV | Buzzer driver |

BK2 uses `maxim,power-cycle-on-init` with a 150 ms delay to recover from
brown-out during rail bring-up.

### PMIC unlock

The MAX20360 locks regulator writes by default. The driver unlocks per rail
before each set/enable operation:

| Register | Address | Role |
|----------|---------|------|
| LockMsk | `0x83` | Selects which functions are locked |
| LockUnlock | `0x84` | Unlock password `0x55`, lock password `0xAA` |

Implemented in `max20360_unlock_regulator()` /
`max20360_regulator_common_init()` inside `drivers/regulator/regulator_max20360.c`.

### Voltage formulas (verified on hardware)

BK1 (MAX20360F):

```
V = 0.55 V + (VSET × 0.025 V)
```

BK2:

```
V = 0.55 V + (VSET × 0.025 V)
```

BBOUT (buck-boost):

```
V = 2.6 V + (VSET × 0.05 V)
```

## Charger Features

Driver: `drivers/charger/charger_max20360.c` (MAX20360 Rev 11).

| Item | Spec |
|------|------|
| Charge voltage | ChgBatReg[4:1]: **4.05–4.60 V / 50 mV** |

| Input limit | ILimCntl[2:0]: 50/90/150/200/300/400/450/1000 mA |

## Fuel Gauge

Driver: `drivers/fuel_gauge/max20360/max20360.c`  
Binding: `dts/bindings/fuel_gauge/maxim,max20360.yaml`

**MAX17260** ModelGauge m5 map (datasheet “MAX17620” is a typo). Cell: 380 mAh,
RSENSE 10 mΩ.

| Property | Register | Scaling |
|----------|----------|---------|
| VCELL | **`0x09`** | 78.125 µV/LSB |
| TAlrtTh | `0x02` | alert threshold (not voltage) |
| REPCAP | `0x05` | 5.0 µVh/RSENSE (0.5 mAh @ 10 mΩ) |
| REPSOC | `0x06` | % = raw/**256** |
| TEMP (pack) | `0x08` | 1/256 °C/LSB |
| CURRENT | `0x0A` | 1.5625 µV/RSENSE |
| TTE | `0x11` | 5.625 s/LSB → minutes |
| AvgTA | `0x16` | thermistor avg |
| DieTemp | `0x34` | die °C (diag helper) |
| TTF | `0x20` | 5.625 s/LSB |
| STATUS.Bst | bit3 | **0=present, 1=absent** |

`power_batt` uses UsbOk + BatGood/BatRegDone + corrected Bst polarity so
**USB-only / no pack → CELL_ABSENT → SOC 0**.

**Capacity units:** Zephyr `FUEL_GAUGE_DESIGN_CAPACITY` is **mAh**; remaining/full
are **µAh**. DesignCap is programmed from DT (`design-capacity-mah = <380>` for
KM20). Remaining/full are ModelGauge estimates (not a direct coulomb ADC
readout); with no pack they are cleared to 0 while design stays 380 mAh.

**USB-only “Charging”:** silicon ChgStat can show CC/CV on a floating BAT pin.
Driver/BLE/UI report **not charging / USB — no battery** when the pack is absent.
Status strip (`ui_shell.c`) draws a compact red battery outline + `!` for pack
fault (20 px strip cannot use scaled 40×40 XIP art). Charge screen
(`power_ui.c`) shows **Battery fault** / `USB - no battery` instead of a
misleading “Charging” + 0%. See [UI_GUIDE.md](../ui/UI_GUIDE.md).

## Troubleshooting

If a PMIC driver Kconfig symbol is undefined or not selectable:

- Confirm the matching devicetree node is `status = "okay"` with the correct
  `compatible` string.
- Confirm `conf/core/pmic.conf` is included in the build overlays.
- For charger only: confirm `drivers/charger/Kconfig` contains
  `rsource "Kconfig.max20360"`.

Regulator / I2C bring-up checks:

- Verify PMIC responds at I2C `0x28` (see `src/core/i2c_probe.c` boot scan).
- Confirm `i2c0` wiring matches `docs/hardware/HARDWARE_REFERENCE.md`
  (SDA=P0.13, SCL=P0.14).
- Check RTT logs from `regulator_max20360` for unlock or voltage-set failures.
- If a rail reads back wrong voltage, confirm the overlay
  `regulator-init-microvolt` matches the intended load.

Fuel gauge checks:

- Confirm the gauge responds at I2C `0x36` (separate from PMIC `0x28`).
- Verify `design-capacity-mah` / `design-voltage-millivolt` match the fitted cell.
- If SOC/current reads fail, check RTT logs from `fuel_gauge_max20360` and confirm
  boot `i2c_probe` sees `0x36`. Errors that start ~10 min after wear often coincide
  with the first auto health cycle (shared `i2c0` traffic) — battery I2C is owned by
  `power_mgr` only; do not call `fuel_gauge_get_prop()` from UI/BLE paths.

### Ship mode / SEAL (`PwrCmd` 0x80)

`regulator_parent_ship_mode()` → `max20360_power_off()`:

1. Unlock (LOCKMASK `0x00`, password `0x55`).
2. Write **`0xE5`** (`PWR_SEAL_CMD`) when `CONFIG_REGULATOR_MAX20360_SHIP_USE_SEAL=y` (default).
3. Or **`0xB2`** (`PWR_OFF_CMD`) when SEAL is disabled.

SEAL is true shipping / lowest Iq; availability depends on OTP `PwrRstCfg`. Wake typically
needs **CHGIN** or **KIN** — test with USB available before factory ship. MCU may lose
power immediately after a successful write; treat I2C success as done.
